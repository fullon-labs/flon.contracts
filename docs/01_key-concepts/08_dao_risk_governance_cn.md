# DAO 分级治理安全模型

`dao.gov` 对可执行提案采用 L1–L4 风险分级。白名单只说明某个 action
技术上允许由治理执行；风险策略进一步规定需要多大的治理基础、参与率、赞成率、
绝对赞成票和等待时间。两者缺一不可。

## 1. 三个独立通过条件

正式投票结束后，提案必须同时满足：

```text
参与率 = (赞成 + 反对 + 弃权) / total_power_snapshot
赞成率 = 赞成 / (赞成 + 反对)
绝对支持率 = 赞成 / total_power_snapshot
```

`finalize` 只有在参与率达到 `quorum_bps`、赞成率达到
`approval_bps`、绝对支持率达到 `min_support_bps` 时才把提案标记为通过。
弃权计入 quorum，但不进入赞成率分母。

## 2. 治理成熟度门槛

每个等级都有 `min_total_power`。`activate` 在创建正式投票快照前检查当前
全网有效 GLON 治理权总量；不足时，即使提案已经获得附议也不能进入正式投票。

推荐主网初始值如下，最终值必须由 `flon` 账户明确配置：

| 等级 | 典型事项 | 最低全网快照票权 | Quorum | 通过率 | 最低绝对赞成 |
| --- | --- | ---: | ---: | ---: | ---: |
| L1 | 文本/信号、普通运营参数 | 1,000,000 GLON | 5% | 50%+ | 1% |
| L2 | 一般经济参数、常规预算 | 10,000,000 GLON | 15% | 60% | 8% |
| L3 | 奖励、质押、处罚等核心参数 | 50,000,000 GLON | 25% | 67% | 15% |
| L4 | BP 席位、治理权限、金库控制、关键升级 | 100,000,000 GLON | 40% | 75% | 30% |

例如 L4 快照总票权为 100,000,000 GLON 时，至少需要 40,000,000 GLON
参与，并且至少 30,000,000 GLON 明确投赞成票；同时赞成票还要达到赞成与反对
有效表态票的 75%。少量账户全部赞成不能绕过绝对支持门槛。

## 3. 链上表和权限

- `riskconfigs`：L1–L4 的最低总票权、三类投票门槛、发起/附议门槛、各阶段时长。
- `actpolicies`：把每个 `contract::action` 映射到风险等级。
- `policysnaps`：记录提案风险等级、累计附议票权以及激活时冻结的安全参数。
- `allowlist`：执行权限、目标 action 和最大 action data 大小。

`setriskcfg` 与 `setactrisk` 都硬性要求 `flon` 授权。这两个 action 不能加入
`dao.gov` 执行白名单，因此 DAO 不能先用低门槛提案降低自己的安全门槛。
生产环境应由 `flon` 的多签权限管理，而不是单一私钥。

所有执行型 action 必须同时存在启用的 allowlist 规则和 action risk policy；
未分类 action 默认拒绝。多 action 提案采用其中最高的风险等级。
文本/信号提案固定使用 L1，但不会执行链上 action。

## 4. 快照与变更规则

提案创建时记录初始风险等级。进入 `activate` 时重新读取 action 分类，只允许风险
等级保持或升高，并把当时的以下字段冻结到 `policysnaps`：

- 全网总票权与最低总票权；
- quorum、通过率和最低绝对赞成率；
- Timelock 与执行宽限期。

之后修改 `riskconfigs` 不会追溯改变正在投票的提案。升级前处于附议阶段且没有
`policysnaps` 的旧提案必须取消并重新创建；已经进入投票阶段的旧提案仍按原快照
完成，以避免解释历史行时发生歧义。

## 5. 配置约束

高风险等级不得比低风险等级拥有更低的最低总票权、quorum、通过率、绝对支持率
或 Timelock。合约在 `setriskcfg` 时检查单调性。建议对 L4 action 额外在目标合约
中设置参数边界、单次变化幅度和冷却期；DAO 通过并不代表可以绕过目标合约自身的
安全检查。
